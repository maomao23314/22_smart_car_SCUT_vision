# 更新日志

## v1.4.0

本次是**易用性修复 + 解耦加固**版本：修掉一批"新人照着文档做却编不过"的坑，
并让环境不再依赖用户算法的具体文件名。

**修复：Dev-C++ 按 F11 不重扫 `code\`，新建文件报 undefined reference**

`code\` 下的文件靠 `env\code_filelist.h` 收集，而那个文件由脚本生成。
VS 每次生成都会自动重跑，命令行脚本也会，**但 Dev-C++ 没有"编译前执行命令"
的功能**，所以按 F11 不会重扫 —— 新建 `myalgo.c` 后按 F11 会报一堆
`undefined reference`，看起来像代码写错了。

- 新增 `tools\rebuild.bat`：重扫 `code\` + 清理过期中间文件，跑一次再 F11 即可
- `README_仿真环境.md` 在 6 处说明这个前提，`一键配置.bat` 结束提示里也加了
- VS 那条路不受影响（`DSH_GenFileList` 每次生成都会执行）

**修复：`code\` 下建子文件夹会直接编译失败**

三个构建辅助脚本只取文件名、丢掉目录名，而扫描又是递归的，于是
`code\algo\line.c` 会生成 `#include "../code/line.c"`，路径不存在 → 编译失败。

- 三个脚本统一支持递归，并保留子目录（`../code/algo/line.c`）
- 顺带修掉"两个不同目录下的同名 `util.c` 会撞车"的隐患
- 三个脚本的扫描规则（`-Recurse`、跳过 `_*` 与 `*.tmp`）现在完全一致，
  避免"能编译但在 IDE 里看不到"这类不一致

**修复：项目路径带空格时命令行编译失败**

`build_dev.bat` 用的是绝对 `-I` 路径且没加引号，路径里有空格就会被拆成两个
参数，报 `gcc: error: Files/...: No such file or directory`。
（仓库放在 OneDrive / 桌面这类带空格的目录下就会踩到。）

- 改为相对路径 `-Ienv -Icode -I.`，与 `.dev`、环境配置指南的写法统一
- `build_dev.bat` 恢复正常输出（原来脚本启动会先打印一行 `echo off`）

**修复：配置 ROI 后示例绘图少一半且位置错**

`main.cpp` 的示例按整幅图高度循环，而 `SCUT_DrawPoint` 的裁剪边界是输出区域
大小。按文档推荐的 ROI 配置（`H=60, Y=60`）改完之后，第 60~119 行的线
**静默消失**，列坐标也没减去 ROI 偏移。

- 循环上界改用 `SCUT_OUT_IMAGE_H`，行列都做坐标换算
- 注释里写清了「图像坐标系」与「显示坐标系」的区别

**改进：图片格式自适应**

读图本来按文件内容判断格式，但文件名只认一个后缀。

- 支持一次配多个后缀（`.bmp,.png`），也支持同一组里格式混着
- 写不带点的形式（`bmp,png`）会自动补点
- 错误提示补充了"图片编号要从 1 开始连续"

**修复：`verify_mixed.ps1` 可能报告假的"全部通过"**

脚本硬编码了 `C:\Program Files\Microsoft Visual Studio\2022` 去找 `dumpbin`。
VS 装在别的版本或别的盘时，MSVC 那半会被静默跳过，却仍然打印
`all 8 checks passed`。

- 改用 vswhere 定位任意版本的 VS（与本仓库其他脚本一致）
- 跳过 MSVC 检查时明确报告"只验证了 MinGW 部分"并以退出码 2 结束，
  不再假装通过

**修复：VS 工程的几个隐患**

- `gen_filelist.ps1` 失败时不再静默继续（`ContinueOnError` 改为 `false`）——
  否则会拿旧的清单去编译，报出与真实原因无关的链接错误
- 文件列表改为递归匹配 `code\**\*.c`，与脚本行为一致

**修复：窗口高度描述与代码不符（文档）**

README 与更新日志称"窗口高度只增不减"，但代码里并没有这个保护 ——
实际是**随日志行数动态伸缩**（日志多时变高、少时回退）。
文档已按实际行为改正，并强调两处高度公式必须同步。

**修复：测试图集数量不一致**

`pic\` 有 120 张，`资源备份\测试图集\` 只有 109 张，两份 README 也各写各的。

- 统一为 **109 张**，`pic\` 六组编号仍为 1..N 连续无缺号
- 两份 README 的数字已一致

**修复：`tools\rebuild.bat` 清理路径写错**

初版硬编码了 `VS\x64\Debug\simu_env.obj` 等两个路径，但它们**都不存在**；
真正存在的 `VS\visual_simu\x64\Debug\simu_env.obj` 反而没被清到。
现在改为扫描 `VS\` 下所有 `simu_env.obj`。

**改进：窗口高度加屏幕上限**

`SCUT_LOG_MAX_LINES` 可以调大，但窗口高度没有上限，调到 60 行会超出屏幕。
现在会夹取到屏幕可用高度以内。

**修复：`disp_env.hpp` 硬编码包含用户头文件 `camera.h`**

`env\disp_env.hpp` 直接 `#include "camera.h"`，而 `camera.h` 是**用户文件**。
于是用户一旦把示例改名或删掉（README 明确鼓励"自己设计算法，不要照抄示例"），
环境本体就编不过 —— 而 `config.h` 却承诺"改宏即可，算法文件一个字不用动"。

- 改为「**存在才包含**」（`__has_include` 探测），环境不再绑定具体文件名
- 详见 `README_仿真环境.md` 关于「环境如何找到用户代码」一节

## v1.3

本次为**单片机移植适配 + 颜色修正 + 计时客观化**版本。

**修复：颜色宏红蓝互换**

`SCUT_COLOR_xxx` 与 Windows/EasyX 的颜色排列不一致，
导致把颜色宏传给图形接口时红蓝互换。现已统一，
并新增 `SCUT_RGB(r, g, b)` 供自定义颜色。
屏幕观感没有变化（红仍然是红）。

> ⚠️ 颜色**不要手写十六进制**，用 `SCUT_COLOR_xxx` 或 `SCUT_RGB()`。

**改进：`code\` 可以原样拷到 CH32 单片机**

- 新增 `code\scut_port.h`，是 `code\` **唯一**的头文件依赖
- 输出数组、尺寸、ROI 全部改为在 `config.h` 里配置
- 新增 `SCUT_OutImageSet(x, y, v)` / `SCUT_OutImageGet(x, y)` 写读输出图像
- 摄像头分辨率 `SCUT_IMAGE_W/H` 也移到 `config.h`
- 算法不再直接碰仿真环境的头文件与显示缓冲

**新增：用 CPU 周期数计时，不再只给微秒**

原来「处理时间」用墙上时间（微秒），会随电脑主频、睿频、系统负载而变 ——
同一份算法在快慢不同的电脑上数字不一样，拿来做考核对比不公平。

现在同时给出 **CPU 周期数**，它是算法自身的固有属性，换电脑也能横向比：

```
处理时间: 41.35 M cycles  (12948.4 us @3194MHz)   (绘图 3.0 us   整帧 155306.9 us)
```

- 以百万（M）为单位，比一长串数字好读；不足 1M 时显示原始周期数
- 启动时自动探测并标定频率，显示在括号里
- 老 CPU / 虚拟机等**不支持稳定周期计时**的机器会自动回退成只显示微秒，
  不会给出不可信的数字
- 按 `R` 做复杂度测试时，两个口径同时平均

**改进：用户算法固定按不优化编译**

`code\` 下的算法显式按 `-O0`（不优化）编译，
Dev-C++、VS、命令行三个工具链口径一致。

原因：若算法被优化（循环展开、中间量消除），测出的周期数就不再反映代码
真实开销，同一写法在不同优化等级下能差好几倍；单片机上通常也不优化，
仿真端不优化才和上车后的表现接近。

> 想测优化后的性能请另开配置，不要拿这里的数字去比。

**修复：示例图上的红线（中线）不再漏画**

现在三条线都在 `main.cpp` 里画：绿=左边界、蓝=右边界、红=中线。

**修复：若干隐藏问题（代码审查发现）**

- **ROI 显示错位**：显示区域比整幅图窄时（用了 ROI），
  输出图像的行定位会算错，画面错位、写入可能越界。
  这个 bug 在「输出图像」相关改动之前就存在，现已修好并逐个像素验证。
- **日志变多时窗口来回跳**：日志加高窗口后，下次重建又按较矮的公式
  缩回去，把日志裁掉，然后再次加高。根因是两处高度公式的行数基准不一致；
  现在统一按当前实际日志行数计算，窗口随日志行数平滑伸缩
  （日志多时变高、日志少时回退），不再抖动。
- **日志回绕后出现过期内容**：日志写满一轮后，窗口重建会把上一轮的
  旧日志又画一遍。现在回绕时一并清掉。
- **长路径导致无限重载**：图片路径超过 260 字符时，热重载会每 300ms
  触发一次、界面一直闪。现在检测到路径过长就放弃监测。
- **采样行写死**：示例里写死了第 90 行，改小图像高度就会越界读。
  改用高度的一半。
- **移植时的隐患**：示例用 `sizeof(mt9v03x_image)` 拷贝输入，
  若移植时把该数组声明成指针，拷贝会静默失效。改用显式字节数。
- **计时行文字重叠**：数字每帧叠着画，会出现「整帧 080709)3 us」
  这种糊成一团的东西。现在每帧先擦该行再写。

**文档**
- `README_仿真环境.md` 新增「搬到 CH32 单片机」一节
- 第六节改写：讲清两种计时的区别、该看哪个、为什么
- 第七节补充 `config.h` 的常见改法（ROI / 换数组 / 换分辨率）
- 「给 AI 的补充说明」新增「踩过的坑」，记录容易反复踩的陷阱

## v1.2


**新增：分开显示三种耗时**

窗口原来只显示一个「处理时间」。现在可以同时看到：

```
处理时间: 12314.7 us   (绘图 1.8 us   整帧 13007.3 us)
```

| 数字 | 含义 | 读法 |
|---|---|---|
| 处理时间 | `image_process()` 耗时 | 环境自动显示 ★ 你要关心的 |
| 绘图 | `draw_image_info()` 耗时 | `SCUT_GetDrawCost()` |
| 整帧 | 处理 + 绘图 + 显示 | `SCUT_GetFrameCost()` |

**为什么绘图不算进「处理时间」**（实测确认）
- 环境只在 `image_process()` 前后取时间戳，绘图在它之后，不在计时区间内
- 这是刻意的：车载程序没有「画点给屏幕看」这件事，
  算进去会让性能数据失真
- 但绘图是真实帧开销，实测 `SCUT_DrawPoint` 画 1000 个点约 11us，
  比一个简单算法本身还慢 —— 所以单独给你看

**新增接口**（`env\scut_display.h`）
- `SCUT_EnableDrawTiming(1)` 打开绘图计时
- `SCUT_GetDrawCost()` / `SCUT_GetFrameCost()`
- `SCUT_Flush(delay_ms)` **强制刷新到屏幕并停顿**，
  用来观察「哪些元素先画、哪些后画」

**修复**
- 整帧耗时原本在画完文字之后才结算，导致显示的一直是上一帧的值（恒为 0.0）

**已知现象（不是 bug）**

按 `R` 测出的时间会比正常帧低，实测差约 37%：

| | 耗时 |
|---|---|
| 第 1 次调用（冷） | 13.5 us |
| 之后 999 次平均（热） | 9.8 us |

原因是第一次执行时指令还没进 CPU 缓存、分支预测器还没学习、CPU 可能还在低频。
**按 `R` 的数字更接近真实性能**，正常帧因为含冷启动而偏高。
这是 CPU 的固有特性，环境不做任何掩盖。

## v1.1

本次为联动与工具链改进版本，可与配套的图像编辑器（`img_editor`）协同工作。

**新特性**
- **热重载**：环境会监测「当前正在显示的那张图片」是否被外部程序改写，
  一变就自动重新读图并重跑算法，不用再手动按 `+` 翻页
  - 配套编辑器保存/上传后即可实时看到算法结果
  - 运行时按 `H` 可随时开关，状态栏显示 `[热重载 开 已刷新 N 次]`
  - 相关配置见 `config.h` 的 `SCUT_HOT_RELOAD` / `SCUT_HOT_RELOAD_COOLDOWN_MS`
  - 实现见 `env\hot_reload.c`（接口 `env\hot_reload.h`）
- 未开新线程：EasyX 的 GDI 对象非线程安全，改用轮询文件属性的方式，
  开销可忽略且不存在数据竞争
- 三重保护避免「算法慢 + 频繁刷新」把程序拖垮：
  写完成判定（签名连续 2 次不变才重载）、冷却时间（默认 300ms）、轮询节流（80ms）

**工具链**
- 新增 `tools\find_msbuild.bat`：通过官方 `vswhere` 自动定位 MSBuild，
  **不再限定 Visual Studio 版本**（2017 / 2019 / 2022 / 后续版本，
  Community / Professional / Enterprise / Build Tools，任意安装盘符均可）
  - 存在多个 VS 安装时，优先选择**确实装了 EasyX** 的那个，
    避免误选 Build Tools 后报 `cannot open include file: easyx.h`
- `一键配置.bat` 重写：适配多版本 VS，同时报告编译器版本与 EasyX 状态
- `build_dev.bat` 改为**自动发现** `env\*.c` / `env\*.cpp` / `*.cpp`，
  不再硬编码源文件列表

**问题修复**
- 修复 Dev-C++ 工程缺少 `env\hot_reload.c` 单元导致链接失败
  （`undefined reference to SCUT_HotReloadInit` 等 6 个符号）
- 修复 `build_dev.bat` 硬编码源文件列表、新增 `env\*.c` 时被静默漏编
- 修复首次拉取代码后编译时，VS 工程项在构建中途才被脚本重写、
  导致当次构建看不到新文件而链接失败的问题
- 修复热重载提示文字与「处理时间」文字重叠

## v1.0

本次为重构版本，在 21 届环境的基础上重写了接口与工程结构。

**新接口**
- 接口统一改为 `SCUT_XXX` 风格，命名与注释格式参考逐飞 CH32V307 开源库的屏幕驱动，便于后续移植到车载程序
- 绘图：`SCUT_DrawPoint` / `SCUT_DrawLine` / `SCUT_DrawRect`
- 日志：`SCUT_Log` / `SCUT_LogAt` / `SCUT_LogClear`，移除了旧的 `PRINT` 接口
- 颜色：`SCUT_COLOR_xxx`，定义在 `env\scut_common_typedef.h`

**新特性**
- 窗口随日志自动加高，日志写不下时不会再被挤掉
- 左键取像素值移到窗口右上角，改用浅蓝色，不再与日志文字重叠
- `code\` 目录自动收集，新建 `.c` / `.h` 无需修改工程设置
- 图片改用相对路径读取，exe 放在哪个子目录都能找到 `pic\`
- 新增 `一键配置.bat`，一次完成文件扫描、编译器与 EasyX 检查、首次编译

**工程**
- 支持真正的 C / C++ 混合编译：`code\*.c` 走 C 编译器，`.cpp` 走 C++ 编译器
- 用户代码不依赖图形库，可直接移植到单片机
- 新增 `tools\verify_mixed.ps1`，用于检查混合编译是否正确
- VS 工程与 Dev-C++ 工程均已配好，打开即可编译运行
- `config.h` 重新整理，用户配置在前、环境参数在后，每项带说明

**问题修复**
- 修复中文显示乱码
- 修复图片读取失败、一直显示渐变图
- 修复切换图片后画面拉伸
- 修复控制台诊断信息不可见
- 修复 `camera.c` 被当作 C++ 编译
- 修复按 `R` 做复杂度测试时日志刷屏
- 修复 Dev-C++ 打开工程后项目列表空白、找不到头文件、项目名乱码
- 修复 VS 通配符警告、按 F5 时新建文件不被编译
- 修复 VS 每次生成后提示「文件已更改，是否重新加载」

**文档**
- 新增 `README_仿真环境.md`（新手上手指南）与本更新日志
