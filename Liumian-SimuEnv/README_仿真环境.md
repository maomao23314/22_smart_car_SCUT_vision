# 流眄 · 仿真环境

> 华工智能车队 · 视觉算法仿真环境

在电脑上模拟 MT9V03X 灰度摄像头。你写纯 C 算法处理灰度图，环境把原图和处理结果并排显示出来。

三件事记住就够了：

1. 跑起来 → 双击 `一键配置.bat`，然后按 F11（Dev-C++）或 F5（VS）
2. 写代码 → 只改 `code\` 里的 `image_process()`，新增 `.c/.h` 不用改工程
3. 看数据 → 输入是 `mt9v03x_image[120][188]`，用 `LM_DrawPoint/DrawLine` 画图，用 `LM_Log` 打数据

算法是纯 C，整个 `code\` 目录原样拷到 CH32V307 就能编译，只依赖 `code\lm_port.h`
（见第十节）。要显示的图像、尺寸、ROI 都在 `config.h` 里配，算法里不写死。

## 一、5 分钟跑起来

### 第一步：配置（只做一次）

双击工程根目录下的 `一键配置.bat`。它会扫描 `code\` 生成文件清单、检查编译器
（Dev-C++ / MinGW / 任意版本 VS）和 EasyX，然后问你要不要立刻编译运行。

### 第二步：日常开发

| 方式 | 怎么做 |
| --- | --- |
| Dev-C++ | 打开 `视觉仿真环境.dev`，按 F11。增删改文件名后先跑 `tools\rebuild.bat` |
| Visual Studio | 打开 `VS\visual_simu.sln`，选 `Debug\|x64`，按 F5（2017 及以上均可） |
| 命令行 | 双击 `tools\build_dev.bat`（MinGW）或 `tools\build_vs.bat`（VS，自动找版本） |

三种方式效果一样，不需要改任何项目属性。

`code\` 下的文件靠 `env\code_filelist.h` 自动收集，那个文件由脚本生成。
VS 每次 F5 都会重新生成，命令行脚本每次也会，这两条路你什么都不用管。

Dev-C++ 没有「编译前执行命令」的功能，按 F11 不会重新扫描 `code\`。
症状是新建了 `myalgo.c`、按 F11、报一堆 `undefined reference to ...`，
看着像代码写错，其实是新文件没被收录。这时双击一次 `tools\rebuild.bat`
再按 F11 就行。只有增删改名文件需要它，平时改代码内容直接 F11。

### 第三步：改代码

打开 `code\camera.c`，把示例算法换成你自己的。

## 三、你要写的代码在哪

`code\camera.c` 里那套大津法 + 跳变扫线只是为了演示接口怎么用：
输入图从哪拿、结果写哪、怎么画线、怎么打日志。

它和真正能上赛道的视觉代码差得很远：没处理十字、环岛、坡道、断路、虚线；
没有边线滤波、补线、丢线保护，跳变点一多中线就乱跳；扫线只取第一个跳变点，
遇到噪点或反光直接跑偏；没有透视变换，也没按行加权；固定按整幅图处理，
没有分区、没有动态阈值、没有置信度判断。

当成 Hello World 看，不是参考答案。你需要自己设计算法，或者参考往届开源方案
（逐飞、各路校赛开源库等）。评的是你的思路和实现，不是有没有照抄示例。

环境只认两个函数，写在 `code\` 目录下：

```c
void image_init(void)       // 开机初始化，调一次。不需要就留空函数体
int  image_process(void)    // 每帧的图像处理主函数，环境自动调用并计时
```

`main.cpp` 里还有两个接入函数：

```c
void draw_image_info(void)  // ① 画点画线，把中间结果显示在图上
void show_image_data(void)  // ② 用 LM_Log 输出数据
```

在 `code\` 里也能画、也能打日志，只要 `#include "lm_display.h"`，示例 `camera.c`
就是这么做的。放哪里随你方便。

### 想加新文件？

直接在 `code\` 下新建 `.c` / `.h` 就行，不用改任何工程设置，也支持子文件夹
（比如 `code\algo\line.c`）。

| 你用哪种方式 | 新建文件后要做什么 |
| --- | --- |
| Visual Studio (F5) | 什么都不用做，每次生成都会自动重扫 |
| 命令行脚本 | 什么都不用做，脚本会先重扫再编译 |
| Dev-C++ (F11) | 先双击一次 `tools\rebuild.bat`，然后照常 F11 |

文件名以 `_` 开头的会被跳过，可以用来临时屏蔽某个文件。

### 环境怎么找到你的代码

`code\*.c` 不是单独编译的，而是被全部 `#include` 进 `env\simu_env.c`。
清单文件 `env\code_filelist.h` 由 `tools\gen_filelist.ps1` 自动生成，
同理还有一份 `env\code_headerlist.h` 列出所有 `.h`。所以增删改名、建子文件夹
都可以，不用动环境。代价是改完文件结构要重跑一次扫描。

有几点可以配置：

- 入口函数名：`config.h` 的 `LM_USER_INIT_FUNC` / `LM_USER_PROCESS_FUNC`。
  改成 `my_vision_init` / `my_vision_run` 也行，签名保持 `void f(void)` / `int f(void)`。
- 不想画示例的三条调试线（左/右/中线）：把 `LM_DRAW_SAMPLE_LINES` 改成 0。
  这三个数组是示例专有的，换了自己的算法后它们就不存在，必须关掉。
  如果你也导出了同名数组就不用改；名字不同的话改 `SAMPLE_LINE_LEFT/RIGHT/MID`。

C 预处理器没有「自动包含一个目录下所有头文件」的能力：`__has_include` 不支持通配符，
也不能 `#include` 一个目录（GCC/MSVC 都报错），更没法判断「某个变量有没有被声明」。
所以只能用生成清单这个办法。

## 四、接口速查

### 输入：唯一的图像来源

```c
mt9v03x_image[y][x]     // y = 行 0~119    x = 列 0~187    值 = 灰度 0~255
```

这个数组是「摄像头」在写的。处理前请先 `memcpy` 一份副本，不要边读边改，
否则会读到半新半旧的数据。`camera.c` 里有标准写法可以照抄。

### 输出图像：在 `config.h` 里指定

输出图像不由你的算法定义，而是由 `config.h` 配置。算法只管用 `LM_OutImageSet()` 写结果：

```c
/* ---- config.h 里这样配 ---- */
#define LM_OUT_IMAGE_ARRAY      output_image   // 要显示的数组名（可以换成你的）
#define LM_OUT_IMAGE_W          188            // 显示区域宽度
#define LM_OUT_IMAGE_H          120            // 显示区域高度
#define LM_OUT_IMAGE_X          0              // 显示起始列
#define LM_OUT_IMAGE_Y          0              // 显示起始行

/* ---- 你的算法里这样写 ---- */
LM_OutImageSet(x, y, 255);        // 往输出图像写一个像素，自动处理 ROI 偏移
uint8 v = LM_OutImageGet(x, y);   // 读回来
```

坐标是相对显示区域的（0 ~ `LM_OUT_IMAGE_W-1`），越界自动忽略。

想只看一块 ROI：把 `W/H` 调小、`X/Y` 改成起点，窗口会自动跟着调整，
算法代码一个字都不用改。

为什么不把输出放 `code\` 里：因为 `code\` 要能直接拷到 CH32 车载工程。
把「显示到哪个数组、显示多大」这类仿真环境的事写进算法，上车就要改代码。
现在这些全在 `config.h`，算法保持干净。

### 绘图

```c
LM_DrawPoint(x, y, LM_COLOR_RED);                 // 画点
LM_DrawLine(x0, y0, x1, y1, LM_COLOR_GREEN);      // 画线（斜线也行）
LM_DrawRect(x0, y0, x1, y1, LM_COLOR_BLUE);       // 画矩形框
```

坐标就是图像坐标，越界会自动忽略，不用自己判断。

颜色用 `LM_COLOR_xxx`，想自己配色用 `LM_RGB(r, g, b)`：

```c
LM_DrawPoint(10, 10, LM_RGB(0x66, 0xCC, 0xFF));   // 自定义颜色
```

不要手写十六进制颜色。`LM_COLOR_xxx` 的内部排列是 Windows 的 `COLORREF`
（`0x00BBGGRR`，蓝色在低位），不是直觉上的 `0xRRGGBB`。直接写 `0xFF0000`
得到的是蓝色而不是红色。用 `LM_RGB(255, 0, 0)` 或 `LM_COLOR_RED` 就永远是对的。

### 日志输出

```c
LM_Log(LM_LOG_LEVEL_INFO, "大津法阈值: %d", thre);
    // 自动排在「处理时间」下面，一行一行往下走

LM_LogAt(420, 560, LM_LOG_LEVEL_WARN, "长度: %d", length);
    // 自己指定窗口坐标（想在右边排一列时用）
```

日志行数超过窗口剩余高度时，窗口会自动变高，不会把文字挤没。
按 R 做复杂度测试时，第 2 次以后的日志会被自动屏蔽，不会刷屏。

### 查询

```c
LM_GetImageWidth();    LM_GetImageHeight();     // 输入图像尺寸
LM_GetOutputWidth();   LM_GetOutputHeight();    // 输出图像尺寸
```

### 耗时与刷新

```c
LM_EnableDrawTiming(1);       // 打开绘图计时
LM_GetDrawCost();             // 上次 draw_image_info() 的花费（微秒）
LM_GetFrameCost();            // 整帧耗时（微秒）

LM_Flush(500);                // 立刻刷新到屏幕并停 500ms，用来看绘制顺序
```

细节见第六节。

## 六、三种耗时，别搞混

窗口上那行字可能长这样：

```
处理时间: 41.35 M cycles  (12948.4 us @3194MHz)   (绘图 3.0 us   整帧 155306.9 us)
```

这是三个独立的量：

| 数字 | 含义 | 怎么来的 |
| --- | --- | --- |
| 处理时间 | 你的 `image_process()` 耗时 | 环境自动计时并显示。这是你要关心的 |
| 绘图 | `draw_image_info()` 耗时 | `LM_GetDrawCost()`，需先 `LM_EnableDrawTiming(1)` |
| 整帧 | 处理 + 绘图 + 显示刷新 | `LM_GetFrameCost()` |

### 「处理时间」为什么给两个数

| 看哪个 | 含义 | 什么时候用 |
| --- | --- | --- |
| M cycles（百万 CPU 周期） | 算法消耗了多少个 CPU 时钟周期 | 对比性能、和同学比、和上次比 |
| us（微秒） | 墙上时间 | 判断实时性够不够（比如要跑满 100fps 就得 <10ms） |

以周期数为主，因为微秒会随电脑快慢变。同一份算法在 3.2GHz 的机器上写 12.7ms，
在 4.5GHz 的机器上可能只要 9ms。数字不一样，但那不是算法变好了，只是电脑更快。

周期数是算法自身的固有属性：它数的是 CPU 时钟周期，与主频解耦
（现代 CPU 的 invariant TSC 特性）。换电脑、开不开睿频、后台有没有别的程序，
这个数字都基本不变。

实测同一段固定工作量：

| | 读数 |
| --- | --- |
| 微秒（墙上时间） | 3863.9 → 4681.0 us，波动 21% |
| 周期数比值 | 3192.5，恒定 |

所以要比算法改进效果，请看 M cycles。

数字不足 1M 时会直接显示原始周期数（如 `12345 cycles`），
避免出现 `0.00 M` 这种看起来像没干活的显示。

周期数也不是物理常数。不同代、不同架构的 CPU（缓存大小、乱序执行、
分支预测能力不同）跑同一份 C 代码，周期数会接近但不完全相同。
它比微秒客观得多，但最公平的比较还是同一台机器上前后对比。

括号里的 `@3194MHz` 是本机自动标定出的 CPU 时钟频率，用来把周期数换算成微秒，
不用手填。如果你的电脑不支持稳定周期计时（很老的 CPU、部分虚拟机），
程序会自动回退，只显示微秒，不会给出不可信的数字。

### 「处理时间」是按不优化编译的

`code\` 下的算法固定按 `-O0` 编译，三个工具链口径一致。

因为算法一旦被优化，编译器会做循环展开、把中间变量消除掉，测出的周期数
就不再反映你写的代码的真实开销，同一份写法在不同优化等级下能差好几倍。
而且单片机上（CH32 车载工程）通常也是不优化或低优化的，仿真端按 `-O0`
才和上车后的表现接近。

想测优化后的性能是另一件事，请另开 Release 配置专门测，不要拿这里的数字去比。

### 为什么绘图不算进「处理时间」

环境只在 `image_process()` 前后取时间戳，`draw_image_info()` 在它之后执行，
不在计时区间内。这是刻意的：车载程序上没有「画点给屏幕看」这件事。
如果把绘图算进去，你优化算法省下的时间会被画一条线就吃掉的开销淹没，
性能数据就失真了。

但绘图仍然是真实的帧开销。实测一个简单算法约 2 µs，
而 `LM_DrawPoint` × 1000 约 11 µs。画得太多会明显拖低帧率，
所以给了你单独的数字去看它。

### 想观察绘制顺序？

`draw_image_info()` 里画的东西默认攒完一帧才一次性显示，所以最终看到的是
所有元素叠在一起，分不出先后。在两次绘制之间调用 `LM_Flush(毫秒)`，
它会立刻把当前内容推上屏幕并停顿，于是能一眼看出哪些是先画的：

```c
for (y = 0; y < LM_IMAGE_H; y++) LM_DrawPoint(left_line[y], y, LM_COLOR_GREEN);
LM_Flush(500);          // 绿线先显示，停 0.5 秒

for (y = 0; y < LM_IMAGE_H; y++) LM_DrawPoint(right_line[y], y, LM_COLOR_BLUE);
LM_Flush(500);          // 蓝线再显示

LM_DrawRect(0, 0, 187, 119, LM_COLOR_RED);   // 红框最后显示
```

`LM_Flush` 只在 `draw_image_info()` 里有意义，在 `image_process()` 里调没效果。
`LM_Flush(0)` 只刷新不停顿。它不影响「处理时间」，绘图和刷新都在计时区间外。
每次调用都会立刻重画整幅图，别调太多次，正式测性能前记得去掉。

## 七、配置文件 `config.h`

分两区，你只需要关心上半部分。

用户配置区可以随便改：摄像头图像尺寸（`LM_IMAGE_W` / `LM_IMAGE_H`）、
要显示的图像（`LM_OUT_IMAGE_ARRAY` 数组名以及 `W` / `H` / `X` / `Y`）、
测试图片路径与后缀、每帧处理重复次数、窗口位置与缩放系数、
日志最大行数、热重载开关与冷却时间。

环境底层参数一般不用改，只有是否保留控制台窗口一项。

每个配置项后面都有一句话说明，打开文件就能看懂。

### 常见改法

```c
/* ① 只看图像下半部分（ROI）—— 算法代码不用动 */
#define LM_OUT_IMAGE_W      188     // 宽度可以不变
#define LM_OUT_IMAGE_H       60     // 只看 60 行高
#define LM_OUT_IMAGE_X        0     // 从第 0 列开始
#define LM_OUT_IMAGE_Y       60     // 从第 60 行开始

/* ② 换个数组显示（比如你想看中间结果而不是最终结果） */
#define LM_OUT_IMAGE_ARRAY   binary_image
#define LM_OUT_IMAGE_ARRAY_TYPE  uint8

/* ③ 换摄像头分辨率（记得测试图也要同尺寸） */
#define LM_IMAGE_W          160
#define LM_IMAGE_H          120
```

改 `LM_OUT_IMAGE_*` 时注意 `X + W` 不能超过 `LM_IMAGE_W`，`Y + H` 不能超过
`LM_IMAGE_H`。超了会在编译期直接报错（环境放了静态断言），不会等到运行时才出问题。

## 八、热重载：与图像编辑器联动

调光照、调曝光这类工作，如果每次都要「编辑器里改 → 另存为 → 回环境按 `+` 翻页」
会很烦。热重载让你省掉后面两步。

### 怎么用

1. 打开环境，翻到你想调的那张图（比如 `pic/1/1.bmp`）
2. 打开图像编辑器，在它右侧的「仿真联动」区里：
   - 目标文件夹 → 指向 `pic\1`（编辑器一般能自动猜出来）
   - 目标文件名 → 填 `1`（也就是你正在看的那张）
   - 勾上「停止操作后自动上传」，等待时间按喜好设（默认 800 毫秒）
3. 在编辑器里随便拖滑块。停手约 800 毫秒后，环境那边会自动重新读图并重跑算法。

不想自动的话，取消勾选，改完点「立即上传到仿真环境」也一样。

### 它是怎么工作的

编辑器把结果写到正在显示的那张图本身，环境监测该文件的时间戳，一变就重读重跑。
所以你翻到哪张就盯哪张，不需要额外目录，也不需要两端直接通信。
对应实现在 `env\hot_reload.c`，对外接口在 `env\hot_reload.h`。

### 几个你可能会关心的点

| 问题 | 处理方式 |
| --- | --- |
| 算法很慢，会不会被刷新拖垮？ | 有冷却时间（默认 300ms），重载请求不会堆积。可在 `config.h` 里用 `LM_HOT_RELOAD_COOLDOWN_MS` 调大 |
| 图还没写完就被读了怎么办？ | 有写完成判定：文件大小加时间戳连续两次不变才认为写完，不会读到半张图 |
| 会不会和手动按 `+` 冲突？ | 不会。翻页时监测目标会自动切到新图，且以切换后的状态为基准 |
| 做性能测试时想排除干扰？ | 按 `H` 关掉热重载，状态栏会显示 `[热重载 关]` |
| 完全不想用？ | 把 `config.h` 里的 `LM_HOT_RELOAD` 改成 `0` |

没有开线程，是因为 EasyX 的 GDI 对象不是线程安全的，多线程改图像缓冲会引入
难以复现的崩溃。这里用轮询文件属性代替，开销可以忽略，且天然不存在数据竞争。

## 九、注意事项

### 编码问题

所有源文件必须保持 `UTF-8 with BOM`。用记事本「另存为」时选 UTF-8，不要选 ANSI；
也不要删掉文件开头的 BOM，否则中文注释会编译报错。

### 关于 C / C++ 混合编译

这个工程是真正的混合编译，不是把 `.c` 当 C++ 编：

| 文件 | 编译器 |
| --- | --- |
| `code\*.c` | C（gcc `-std=c11` / MSVC `/TC`） |
| `env\simu_env.c` | C（它负责包含 `code\` 下的所有 `.c`） |
| `main.cpp` | C++（g++ `-std=c++17` / MSVC `/TP`） |
| `env\disp_env.cpp` | C++（EasyX 只能用 C++） |

所以你在 `code\` 里写的是真 C：变量声明要放在块的开头，不要用引用、模板、
`new/delete`、类这些东西，也不要 include easyx 之类的图形库，
这样算法才能直接上单片机。

想验证这一点，可以跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\verify_mixed.ps1
```

## 十、搬到 CH32 单片机

整个 `code\` 目录只依赖一份头文件 `code\lm_port.h`，不包含仿真环境的任何其他头文件
（`lm_display.h` / `simu_env.h` / `config.h` 都不碰）。所以上车时：

```
把 code\ 整个目录拷到你的 CH32 工程里  →  直接编译  →  完成
```

不需要改算法代码的任何一行。

### 你要做的只有一件事：提供 `lm_port.h` 里那几个实现

| 声明的符号 | 仿真环境里的实现 | 车载工程里怎么做 |
| --- | --- | --- |
| `mt9v03x_image[120][188]` | 环境读 BMP 填进去 | 指向摄像头驱动的图像数组（逐飞库通常同名） |
| `LM_OutImageSet/Get` | 写显示缓冲 | 写 IPS 屏显存，或写你自己的图像数组 |
| `LM_DrawPoint/DrawLine/DrawRect` | EasyX 画到窗口 | 画到 IPS 屏；不需要就直接删掉这些调用 |
| `LM_Log/LogAt/LogClear` | 显示在窗口下方 | 接串口打印；不需要就直接删掉 |

最省事的做法：在车载工程里新建一个 `lm_port_mcu.c`，把这几个函数写成空函数，
先把算法跑起来，之后再逐个接到真实的屏幕或串口上。

### 如果车载工程已经有同名类型或颜色宏

`lm_port.h` 已经预留了开关，在你的工程里提前定义即可跳过对应的定义段：

```c
#define LM_PORT_HAS_TYPES     // 你已经有 uint8/int16 等类型（逐飞库就有）
#define LM_PORT_HAS_COLORS    // 你已经有 LM_COLOR_xxx
#define LM_PORT_HAS_LOGLEVEL  // 你已经有 lm_log_level_enum
```

单片机（IPS 屏）的颜色通常是 RGB565，和仿真环境的 `COLORREF` 排列不同。
如果你要用屏自带的颜色宏，就定义 `LM_PORT_HAS_COLORS`，让车载工程的颜色定义生效，
两边不要混用。

### 在仿真环境里它自己是怎么工作的

仿真环境会把 `code\*.c` 全部 `#include` 进 `env\simu_env.c` 这一个编译单元。
此时 `lm_port.h` 会发现环境侧的 `lm_display.h` 已经在场，于是自动跳过自己那份定义，
直接用环境的，两边不会重复定义。这个判断就是 `lm_port.h` 里的
`LM_PORT_STANDALONE` 宏，你不用管它。

### 验证移植是否真的没问题

仓库里可以直接验证 `code\` 单独拿去能不能编：

```powershell
# 只拷 code\ 下的文件（不带 env\），用 gcc 以 C11 编译
gcc -std=c11 -Wall -Wextra -I code -c code\camera.c -o build\camera.o
```

能编过且无警告，就说明算法侧是干净的。

### 图片没显示出来？

窗口里出现一张渐变图 = 图片读取失败，检查 `config.h` 里的 `LM_PIC_DIR` / `LM_PIC_EXT`，
默认是 `"pic/1"` 和 `".bmp"`。图片编号必须从 1 开始连续，环境靠文件名统计每组多少张。
程序启动时会自动把工作目录切到工程根目录，所以不管 exe 落在哪里都能找到 `pic\`。

### 编译报错说找不到 `easyx.h`

图形库没装好。Dev-C++ 环境按 `资源备份\环境配置\环境配置指南.md` 安装 `easyx4mingw`；
VS 环境装 EasyX 官方安装包（会自动放进 VC 目录）。

## 十一、常见问题

| 问题 | 解决办法 |
| --- | --- |
| 窗口显示一张渐变图 | 图片没读到，检查 `config.h` 的 `LM_PIC_DIR` / `LM_PIC_EXT` |
| 中文显示成乱码 | 源文件必须 `UTF-8 with BOM`，不要存成 ANSI |
| 找不到 `easyx.h` | 装 EasyX（见第十节末） |
| 自己加的 `.c` 没被编译 | 先看文件名是不是以 `_` 开头；否则是 Dev-C++ 没重扫，跑一次 `tools\rebuild.bat` 再 F11 |
| 画出来颜色不对（红蓝反了） | 别手写十六进制颜色，用 `LM_COLOR_xxx` 或 `LM_RGB(r,g,b)` |
| 改了输出尺寸/ROI，算法读不到图 | 输出用 `LM_OutImageSet/Get`，坐标相对显示区域；不要直接用 `output_image[y][x]` |
| 编译报 `lm_out_roi_check` 负数组 | `X + W` 超过 `LM_IMAGE_W`，或 `Y + H` 超过 `LM_IMAGE_H`，改 `config.h` |
| 拷到单片机编译不过 | `code\` 里只应 `#include "lm_port.h"`；若还包含了 `lm_display.h` / `config.h` 就是违规了 |
| Dev-C++ 打开后项目列表是空的 | `.dev` 必须保持 GBK 编码 + CRLF 换行，别用编辑器存成 UTF-8 |
| 日志太多挡住帮助信息 | 不会，窗口会自动变高；想限制行数改 `LM_LOG_MAX_LINES` |
| VS 提示「VC 项目不支持通配符」 | 已经修掉了。若你自己加了通配符请改回具体文件列表 |
| VS 里按 F5 找不到 `pic` | 不应出现。环境会自动切工作目录，`.vcxproj.user` 也设了调试工作目录 |
